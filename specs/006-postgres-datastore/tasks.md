# Tasks: Durable Multi-Writer Metadata Store

**Input**: Design documents from `/specs/006-postgres-datastore/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md),
[data-model.md](./data-model.md), [contracts/](./contracts/), [quickstart.md](./quickstart.md)

**Tests**: Included, because **FR-026 requires them**: "Automated tests MUST exercise the
integrity rules in FR-008 through FR-013 against that same engine, so a violation cannot pass
tests and fail in production." This is not a TDD preference — it is a requirement of the spec,
and it is the only thing that distinguishes this migration from one that looks finished and
loses somebody's credits at 8pm on a Sunday.

**Organization**: Tasks are grouped by user story. Note the shape of *this* feature before
reading the phases: the spec says of US1, *"Delivering this story necessarily delivers the
whole store replacement."* So Phase 3 is large and Phases 4–5 are small. That is the spec's
own priority ordering, not an imbalance to correct.

- **[P]**: Can run in parallel (different files, no dependencies)
- **[Story]**: Which user story this task belongs to (US1, US2, US3)

## Dependencies & Execution Order

- **Foundational (Phase 2)**: Depends on Setup — **blocks everything**
- **US1 (Phase 3)**: Depends on Foundational
- **US2 (Phase 4)**: Depends on US1 — there is nothing worth backing up until the platform runs on Postgres

- **Polish (Phase 6)**: Depends on all three stories

### A note on story independence

The template assumes stories are independently deliverable. **US2 and US3 genuinely depend on
US1 here**, and pretending otherwise would produce a misleading plan. The spec says so
directly: *"Delivering this story necessarily delivers the whole store replacement, which
makes it the smallest slice that stands on its own."* US1 is not the first slice of the
migration — it **is** the migration. US2 and US3 are what the new store makes possible.

Each story remains independently *testable*, which is what matters for validation: US2 is
proven by a restore rehearsal, US3 by a rolling deploy under traffic, neither needing the
other.

## Implementation Strategy

### MVP (User Story 1 only)

1. Phase 1: Setup
2. Phase 2: Foundational — **the suite goes red here, and that is expected**
3. Phase 3: User Story 1 — green again at T024, correct at T031–T034
4. **STOP and VALIDATE**: 408 tests plus the concurrency tests green; walk the screens (SC-007)
5. Deploy with `replicas: 1`

At that point the platform is on Postgres, contention failures are gone, and the credit
invariants are enforced by the store. Backups and no-downtime deploys are still missing —
which is exactly the priority order the spec argues for.

### Incremental Delivery

1. Setup + Foundational → the harness works
2. US1 → the store is replaced → **deploy (MVP)**
3. US2 → recovery exists → rehearse it
4. US3 → deploys stop being outages
5. Polish → docs, verification, the SC checklist

### The two steps most likely to break something

- **T013–T024** touch every query in the codebase. Nothing proceeds until all 408 tests pass.
- **T028** changes the money path. It needs T031 to prove it, which is why the test follows
  immediately rather than being deferred to a testing phase at the end.
